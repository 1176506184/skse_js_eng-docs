完整收集任务流程

此教程提供一份可安装的完整脚本，把角色、事件、物品、对话与任务存档连接起来。纯逻辑回归已通过；新增原生事件、库存处理和对话菜单接入尚待游戏内验证。

流程

生成并缓存旅人 NPC → 交谈接取委托 → 收集 3 朵蓝色山花 → 再次交谈实际交付 → 再次交谈领取 50 金币 → 完成并保存。

示例仅依赖 Skyrim.esm。原生任务日志需要启用 SkyrimJS_Tasks.esp；缺失时 JS 进度仍工作。无需 MilkModNEW。

安装示例

源码仓库示例位于 examples/collection-quest.js。也可直接 下载完整脚本，以 UTF-8 保存为 Data/SKSE/Plugins/SkyrimJS/main.js。需同时使用这一轮构建的 DLL，旧 DLL 没有事件和库存查询方法。

在仓库目录运行安装脚本，路径替换为游戏实际目录：

powershell
./scripts/install-collection-example.ps1 -GameDirectory 'G:/Demo/SKSEMOD/SkyrimSE'

安装器检查游戏已退出，先备份原来的 DLL、main.js 与任务载体，再复制新文件并核对 SHA256。备份放在 Data/SKSE/Plugins/SkyrimJS/backups/collection-时间戳-随机值。它不会修改源码里的 examples/main.js，也不会启动游戏。MO2 用户应把相同文件放到实际启用的模组配置中。

通过 SKSE 重新启动游戏，继续一个测试存档。首次生成旅人后约 1.5 秒尝试展示委托对话；未自动打开时靠近旅人按交互键。重复读档会使用缓存 NPC。

游戏中操作

  • 选择“交给我吧。”接取任务。选择暂时没空不会创建任务。
  • 到世界中拾取蓝色山花；任务目标显示实际库存，未收集齐时丢弃物品会降低进度。
  • 示例默认 DEMO_ITEMS = true，收集阶段与旅人交谈可选“演示：领取 1 朵测试山花。”，重复操作三次可走通流程。正式模组改为 false。
  • 收集齐后与旅人交谈，选择“交付 3 朵蓝色山花。”。物品会从玩家背包转到旅人背包。
  • 再次交谈，选择“领取 50 金币。”。金币增加后最后一个目标完成。
  • 再次交谈或保存后重启读档，不应重复发钱；原生任务日志的显示也需要一并检查。

也可自行打开游戏控制台输入 player.additem 00077E1C 3，测试原生获取物品事件；本工具不会自动执行游戏控制台命令。

核心 API 组合

js
const flower = Skyrim.getForm("0x077E1C");
const task = player.addTask({
    id: "myMod.flower-delivery",
    title: "山花委托",
    steps: [
        { title: "收集蓝色山花", total: 3 },
        { title: "交付山花" },
        { title: "领取报酬" },
    ],
});
const sync = () => {
    if (task.state === "active" && task.currentStep === 0) {
        const count = player.getItemCount(flower);
        if (Number.isInteger(count)) task.steps[0].setProgress(count);
    }
};
const offAdded = player.on("itemAdded", sync);
const offRemoved = player.on("itemRemoved", sync);
sync();

完整脚本还会过滤物品事件、记录交付收据、确认双方库存变化，以及在结束后移除收集监听。上面仅展示组合关系，交付与发奖应使用完整示例的检查。

存档与防重复

数据Storage / 任务 ID
旅人引用demo.blue-flowers.npc
任务demo.blue-flowers.v1
结算收据demo.blue-flowers.receipt

收据先记 transferPending，再执行转交，核对双方数量后记 delivered。领奖先记 rewardPending，确认金币增加后记 rewarded，最后完成任务。

读档只根据 delivered / rewarded 修复未完成的目标，不重新执行转交或发钱。pending / Uncertain 表示调用或记账中断，暂停重试并打印收据。确认引擎未改变任何数量的失败才允许重试。NPC 死亡会使未完成任务失败；已经完成的任务不会变成失败。

这不是游戏存档与物品操作之间的通用事务协议。其他模组修改数量、Storage 满或异常中断时，暂停需要人工核对。不要直接删除 pending 来强行重试；先检查玩家/NPC 背包和日志，再修复收据。恢复 rewarded 不会重复发钱。示例没有删除任务或重玩同 ID 的入口，想重新试验可使用未接取任务的存档。

进度规则

收集阶段使用 setProgress，背包减少会回退未完成目标；一旦收集目标完成，目标不会重新锁回。交付时再次检查实际库存，所以收集齐后丢弃/出售仍无法交付。目标完成不等于物品已交付，领奖只在确认转交成功后开放。

示例按基础物品计数，不区分被偷、强化、附魔等实例；正式模组如果需要这些条件，需要增加相应实例与所有权 API。

日志与排查

所有示例日志以 [委托] 开头。原生事件初始化应有 Events: activate, inventory, death and combat sinks registered。

  • 角色没出现：检查 onMounted、skse.new 与 Storage 日志。
  • 按交互键没有自定义选项：检查 setTopic 的请求、displayed 与错误日志，并确认没有其他 NPC 对话占用菜单。
  • 进度不动：确认 getItemCount 返回整数，物品是 00077E1C；重新与旅人交谈会对账。
  • 日志未显示任务：检查 SkyrimJS_Tasks.esp 已在当前配置启用，以及 task.journal 状态。
  • 收据异常：查 demo.blue-flowers.receipt；不要重复交付或自动整笔发奖。

已做的验证

8 项任务核心测试与 8 项完整示例逻辑测试通过，共 16 项。示例测试覆盖正常流程、拒绝接取、已有库存、丢弃、读档、引擎拒绝、部分转交异常、记账中断、确认收据恢复和 NPC 死亡。测试使用模拟的角色、库存和事件，不能代替游戏内原生行为验证。未启动游戏、开发服务或 TypeScript 检查。
